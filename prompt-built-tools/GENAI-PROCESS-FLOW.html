Shop load flow

As soon as JCNs (job control numbers) start arriving for a project, see what each one does to the shop load, before planning has happened. As the planning floor catches up, its estimates and scheduled dates replace the guesses from history, so the map gets more real as the availability gets closer.

1 · Source · the reporting tool, connected to the yard database

Pull the exports

the reporting tool can pull almost anything once the pull is worked out. Field names stay generic here; the real names come out of the reader step below. Each pull is a workbook (.xlsx) or a sheet saved as CSV.

History (the estimator's memory)
  • JCN history: one row per JCN with its job summary, project, hull, class, SWLIN, space, equipment, received date have
  • Tasks: one record per task of a phase of a job summary (the shop, the task, the crew size, the estimated and charged hours, who performed it), with the phase's title, description block and planned and actual dates repeated on each; the tool derives the phases from it have
  • Material: one row per item per end-use phase have
  • Who did each phase: organic shop or contractor to pull
The future (what the estimator scores)
  • Work package: the JCN list for future projects, same columns as the history minus the outcomes. From the reporting tool for all future projects at once, or from the JCN database per project; the JCN database copy carries the in-house or farm-out mark from screening, the the reporting tool copy does not to pull
  • Planning status per job summary: planned yes or no, the planner's man-days by shop, scheduled phase dates to pull
  • Project list: project, hull, start and end dates validate (believed to be on the workforce map)

4 · Tool · the estimator (history plus comparison engine)

Score every future JCN against the past

For each JCN in the work package, the comparison engine finds the most similar completed work (same class first, then equipment, space, SWLIN) or says it found none. A job summary that planning has already estimated skips the guess and carries the planner's numbers instead.

In
  • JCN history, phases, material (as .xlsx or CSV)
  • The work package: future JCNs for all future projects
  • Planning status: which job summaries are planned, their shop man-days and scheduled dates
  • Project list with dates, so "20% through the avail" has a calendar to land on
Out · one line per job per phase per shop
  • Phases and shops: the newest analog's work breakdown, one line per phase and shop, with that shop's tasks as text
  • Material: per phase, every stock number the similar jobs ordered, with nomenclature and quantity, and which analog it came from
  • Duration and man-days per shop, low and high
  • When in the avail: week N or the fraction of the availability where the analogs ran
  • Planned or guessed, organic or contractor, the analogs used, "no match" flagged rather than dropped
consumption.csv + workforce map + project list + project lookup
5 · Tool · the resource leveler (the map)

Which jobs consume which shop, when

Every shop, every week: what the workforce map already assigns plus what the estimator says is coming, against the shop's capacity, with the contractor read as its own line. The dates of record are the baseline; everything you drag is a what-if on top of it.

Do
  • Click an overloaded shop-week: the work in it expands to a job list have (drill-down)
  • Drag a job left or right, week to week (a chip onto a week, or 1-week buttons) have
  • Drag a whole project left or right (the projects strip) have
  • Zoom to a time frame, then snapshot it (PNG for the TVs, present mode) have
  • Level and farm out automatically inside each project's window, then compare before, leveled and farmed have (suggestions until Apply)
Out
  • Shop by week load as CSV, pivots in Excel have
  • Moves list: every job or project you dragged, from and to, for someone to key into the schedule of record have
  • Farm-out list: every job on the contractor's line and why (screening, planning, a guess from the analogs, or by hand) have
  • Snapshot (an image of the map for a time frame) for the TVs around the command

6 · People

Who looks, who decides

  • You and the chief engineer: the what-if. Move a project, farm out, lend people, and see the year change.
  • Planners: what is coming before they plan it, and which guesses their estimates will replace.
  • The shops, through the TVs: "shop 11 is going to be way overloaded in that stretch" or "fine this time frame", at a glance.
  • Back to the reporting tool: nothing writes to the system of record. The moves list is keyed in by whoever owns the schedule.
The loop that makes it get more real

Every new the reporting tool pull carries more planned job summaries and more scheduled phases. The estimator skips those and keeps guessing only the unplanned ones, so the map is a mix of planner numbers and history numbers, and the mix shifts toward planner numbers as the availability approaches. Closed jobs become history on the next pull. Deficiency hours (the work the package did not predict) are not in this loop yet; they are the reason history understates effort.

The holes, and what closes each

You said you left gaping holes. These are the ones I can see from the dump and from what is already built.

1

Project identity built

The workforce map names a project its own way (name, fiscal year, hull type) and nothing else in the system uses that name. The estimator output and the workforce map cannot be joined without a bridge.

Closes it: one lookup sheet, workforce map project name to the project id the JCN history uses, kept by you as a CSV the map imports. The reader prompt can draft it from the two exports; you confirm each row.

Built 2026-10-23: the Resource Map imports lookup.csv (map_name, project, hull) and shows the workforce map's hours under the estimator's project id; Prompt L in the build guide drafts the file from the two name lists.

2

Project dates one file

"When in the avail" only lands on a calendar if every future project has a start and an end. You think the workforce map has them; not checked.

Closes it: Prompt A on the workforce map says whether the dates are there. If not, a the reporting tool pull of project, hull, start, end.

2026-10-23: either way the map takes a projects.csv (project, hull, start, end); the automatic leveler moves a job only inside its project's window, so a project without a row never moves.

3

Planned versus guessed built

The estimator must know which job summaries planning has already estimated, so it carries those numbers instead of guessing. That is a field the current pulls do not have.

Closes it: add to the work package pull, per job summary: planned (yes or no), the planner's man-days by shop, and the scheduled start and finish per phase where they exist. The estimator rule is then one line: planned rows pass through, unplanned rows are scored.

4

The contractor, about 35% of the work estimator side built

Three separate questions hide here. Which past phases were contractor work (otherwise their hours inflate the organic estimate). Which future jobs will go to the contractor (not known until planning, so before that it is a guess from the analogs). And how the contractor's capacity line on the workforce map is read (as one more shop, by your description).

Closes it: a performing-activity field on the phases pull (organic shop or contractor); the contractor read as a shop on the map; a contractor job's own man-hour estimate treated as a planned estimate. For a future job, the in-house or farm-out mark from the JCN database screening when the work package comes from there; otherwise the analogs' majority, flagged as a guess.

5

Dragging changes a plan nobody keeps built

A drag moves hours on the map, and nothing on the work computer can write that back to the schedule of record.

Closes it: the map exports a moves list (job or project, from week, to week, who moved it, when) as the hand-off. It is a what-if tool until someone keys the moves in, and the page says so.

Built 2026-10-23: moves are an overlay on the loaded files, listed with who and when, undone one by one or all at once, exported as moves.csv; the leveler's own moves are marked auto and discarded as a group.

6

What "amount of material" means decided

Decided 2026-10-22: per phase, every stock number (NIIN, national item identification number) the similar jobs ordered, its nomenclature and its quantity. The material export already carries those three, so no new field.

Decided 2026-10-23, grouped JCNs: when several JCNs sat on one job summary, the hours are shared out over them (divided by the count, as the estimator has done from the start) but the material is not. Each new JCN that matches a grouped summary gets the complete list at full quantity, and a group_size column says how many JCNs the bundle held, so a planner can trim a list that may carry sibling jobs' parts.

Closes it: a material estimate file out of the estimator, one row per analog material line per phase, naming the analog it came from and the size of the bundle it came from (built; Prompts D v0.4).

7

Timing in the avail needs two things the history may not carry

"Historically we do this in week 5" needs, for every past JCN, the project it ran under and that project's start and end. You said the history export can carry the project; the availability dates would be a second small pull.

Closes it: project on each history row, and a project list with dates covering the history years. The placement rule (same fraction of the availability as the analogs) is already in the batch prompts.

8

Emergent and deficiency work decided

Tonight's dump is about the work package. The earlier design also loaded an emergent reserve per shop from history (JCNs received after the availability started), and you have said deficiency forms add hours that never feed back.

Decided 2026-10-22: later. V1 maps the work package and the workforce map only; the reserve comes back once real exports work.

9

HTML and JavaScript, or something else

Rust or anything compiled needs a binary file a chat model cannot type out, so it cannot be built inside GenAI.mil. The Power Platform route has the data-shaping problem you named. Standalone HTML with JavaScript is the only route where the whole build is text that passes through a prompt window.

Stands: several small HTML files, CSV between them, each built from its own prompt series. The browser's own database inside each file carries the big tables.

10

Looks built

The built pages are plain because the prompts never asked for a look. The demo's look is a stylesheet of about sixty lines plus a different map cell (a color square, the number on hover).

Closes it: one style prompt, tested the same way as the others, applied last in every series. Light and dark, dashboard layout, zoom to a time frame, snapshot as an image.

Built 2026-10-23: Prompt S carries the demo's stylesheet and the square-cell rule; zoom, snapshot and present mode are in series B2. Tested on both tools; the functional tests still pass on the styled pages.

Material, history have

As today: job summary, end-use phase, stock number (NIIN or NSN), nomenclature, quantity. Add the unit if the export has one. Shape (the owner, 2026-10-23): one row per order line per phase of a job summary. The JCN history is what repeats a grouped summary once per JCN; the material does not, and the tool takes its rows as they are. If a pull ever lists a line once per JCN, say so before loading it, because the tool would add the copies up.
